# 从既有部署并入的改动

本分支在 v0.4.0 之上并入两处已经过实际部署验证的改动。选择标准：对其他自建网关也可能有用，并且不携带部署方信息。仅对某一种部署有意义的定制没有并入，理由列在最后。

## 一、429 时切换到第二把上游 key

**问题**：单个上游账号被限流（429）时，原逻辑要么换池成员，要么把 429 直接交给客户端。只配一个上游、但手里有两把 key 的部署没有中间选项。

**做法**：provider 配置新增可选字段 `api_key_env_2`，指向另一个环境变量。请求返回 429 时，退避 1 秒，把鉴权头换成第二把 key 重试一次；仍失败则回到原有逻辑（换成员或错误收尾）。

```json
{
  "providers": {
    "example": {
      "base_url": "https://api.example.com/v1",
      "api_key_env": "EXAMPLE_KEY",
      "api_key_env_2": "EXAMPLE_KEY_2"
    }
  }
}
```

**边界与代价**：

- 每轮请求只轮换一次，不无限重试；轮换后仍 429，继续走原有的协议切换与成员切换。
- 只替换鉴权头（`Authorization`、`x-api-key`、`x-goog-api-key` 三者中存在的那一个），请求体、会话 id、其余请求头不变。
- 轮换会产生一次真实的上游请求，因此可能产生一次额外调用；只有第一把 key 被限流时才会走到这一步。
- 日志只记 provider 与模型名，不记 key 值；统计里的状态码取轮换后那次响应的结果。
- 只覆盖 chat 中枢；原生直通路径（Responses / Messages / Gemini）未加这一步，因为它们的重试与池切换语义不同。
- 未配置 `api_key_env_2` 时，行为与 v0.4.0 一致。

## 二、只读作用域（scope=quota）

见 `docs/readonly-quota-key.md`。给监控类客户端发一把只能读模型清单与额度、不能对话与生成的 key。

## 三、没有并入的差异

这些在既有部署中使用过，但要么上游已用更完整的机制覆盖，要么属于部署私有，不适合放进公开分支：

| 既有实现 | 未并入的原因 |
|---|---|
| 流式响应每 15 秒发一行 SSE 注释 | v0.4.0 的 `startFirstByteHold` 已提供首字节前的保活机制，未重复实现 |
| 推理档位不支持时就近降级 | v0.4.0 的 `effortsForModel` 与档位探测已处理，重复实现会形成两套判定 |
| 额度查询的三个独立函数 | v0.4.0 的 `computeQuotaSnapshot` 已聚合同类数据，并带缓存与单飞 |
| 面板页脚、站点名称、主题色 | 部署私有，公开分支不带实例特征 |
| 客户端 key 的命名与备注 | 使用方的运营约定，不是网关能力 |

## 四、验证

1. `node --check server.mjs` 通过。
2. 未配置 `api_key_env_2` 时，一次普通对话返回 200，请求路径与 v0.4.0 相同。
3. 配置两把 key、并让第一把 key 返回 429 的测试环境里，日志出现 `UPSTREAM 429 KEY ROTATE`，且请求最终成功。
4. 只读 key 的验证清单见 `docs/readonly-quota-key.md`。
